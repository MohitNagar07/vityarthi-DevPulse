2. Introduction

Modern software engineering is dominated by distributed microservices, RESTful APIs, and cloud-native infrastructure. Software systems are split into dozens or hundreds of decoupled services that interact over the network. In such complex environments, network degradation, latency spikes, and sudden service outages can cascade through interdependent components, severely undermining user experience and business operations.

While enterprise Application Performance Monitoring (APM) tools such as Datadog, New Relic, and Dynatrace provide rich observability, they introduce significant drawbacks: they are resource-heavy, closed-source, require complex agent installations, and depend on browser-based graphical user interfaces. When software developers, DevOps practitioners, and system administrators operate in terminal environments (such as remote SSH bastion hosts, containerized Linux runtimes, or automated continuous integration runners), heavy GUI applications are impractical.

DevPulse is engineered to bridge this gap. It is an autonomous, lightweight, and high-performance Command-Line Interface (CLI) application built exclusively in pure Java (JDK 11+) with zero external third-party dependencies. DevPulse leverages asynchronous non-blocking multithreading (CompletableFuture and java.net.http.HttpClient) to poll dozens of remote endpoints concurrently, benchmark response latency with hardware timers, compute live SLA uptime percentages, and persistently log failure incidents to disk.

3. Problem Statement

System administrators and software engineers managing distributed web applications face several recurrent operational hurdles:

  • Tedious Manual Verification: Manually checking endpoint availability using native curl or basic ping commands is sequential, time-consuming, and lacks structured aggregated metrics.
  • Lack of Terminal-Native Concurrency: Sequential HTTP query scripts scale linearly ($O(N)$) with network latency. Probing 50 separate endpoints with an average latency of 200ms requires 10 seconds sequentially, leading to outdated health metrics.
  • Absence of Persistent Benchmarking & Incident Auditing: Ad-hoc terminal scripts lack built-in local configuration persistence, historical latency distributions (min/avg/max), and automated incident event logs.
  • Resource Overhead of GUI Monitors: GUI and web-based monitoring dashboards consume hundreds of megabytes of RAM, rendering them unsuitable for minimal cloud servers and headless development environments.

DevPulse resolves these issues by providing a high-performance terminal CLI that concurrently pings all monitored targets, displays color-coded ASCII health tables, tracks session SLA percentages, records outage events to a local audit log, and manages targets through an interactive menu.

4. Functional Requirements

The system is architected around three cohesive functional modules:

4.1 Module 1: Service Registry & Configuration (CRUD)

  • Add Endpoint: Allows users to register new HTTP/HTTPS targets with a descriptive name, target URL, expected HTTP status code (default 200), and timeout threshold (1–60s).
  • List Endpoints: Renders a formatted tabular ASCII overview of all monitored endpoints, their unique IDs (EP-xxx), URLs, and configurations.
  • Update Endpoint: Allows modifying existing endpoint attributes with sensible fallbacks to retain existing values.
  • Delete Endpoint: Allows removing endpoints with explicit confirmation to prevent accidental loss.
  • Persistence: Automatically persists all modifications to data/endpoints.csv using RFC-4180 compliant escaping and atomic temporary file swaps.

4.2 Module 2: Polling & Metrics Engine

  • Asynchronous Concurrent Polling: Probes all registered endpoints concurrently using a bounded thread pool and Java's HttpClient. Total batch check duration is bounded by the slowest single request ($\max(t_i)$).
  • High-Precision Latency Benchmarking: Measures round-trip network response duration with sub-millisecond precision using System.nanoTime().
  • Fault Handling & Error Classification: Maps network outcomes to distinct statuses: UP, DOWN, TIMEOUT, and ERROR, gracefully handling DNS resolution failures, connection refusals, and SSL certificate handshake errors without crashing.

4.3 Module 3: Analytics, Reporting & Alert Auditing

  • Real-Time Terminal Dashboard: Renders status badges ([OK] UP, [FAIL] DOWN, [WARN] TIMEOUT, [ERR] ERROR), HTTP status codes, latency, and diagnostics.
  • SLA Uptime Computation: Evaluates session uptime percentage: $\text{SLA} = (\text{Successful Checks} / \text{Total Checks}) \times 100$.
  • Latency Distribution Statistics: Computes minimum, maximum, and average response latency per target across successful HTTP responses.
  • Incident Event Auditing: Automatically logs timestamped failure events to logs/health_events.log.

8. Design Decisions & Rationale

# Architectural Decision Alternatives Considered Engineering Rationale
1 Zero External Dependencies (Standard Java 11+) Apache HttpClient, Jackson, or Retrofit Guarantees effortless compilation on any machine with JDK installed; zero security vulnerabilities from external libraries; zero build-tool setup friction.
2 Asynchronous Parallel Polling (CompletableFuture) Sequential single-threaded polling Sequential polling scales linearly ($O(\sum t_i)$). Parallel polling scales as $O(\max(t_i))$, completing 5 pings in ~1.3 seconds rather than 5+ seconds.
3 Atomic Temporary File Swapping Direct file truncation (TRUNCATE_EXISTING) Direct writes risk empty or corrupt configuration files if the process is terminated mid-write. Writing to .tmp and swapping via ATOMIC_MOVE guarantees data integrity.
4 Memory-Bounded Circular Buffer (ArrayDeque) Files.readAllLines Files.readAllLines loads entire files into heap memory, causing OutOfMemoryError on large logs. A bounded queue keeps memory consumption constant ($O(\text{tail})$).
5 Visual Width Padding (stripAnsi) Standard printf string formatters ANSI escape codes have non-zero character length but zero visible width, causing ASCII borders to stagger. Calculating true visible length creates aligned tables.

9. Implementation Details

Key algorithmic highlights implemented in the codebase include:

9.1 Parallel Polling Engine (PollingEngine.java)

Utilizes CompletableFuture.supplyAsync bound to a custom thread pool sized according to CPU cores (Math.min(32, cores * 2)) to dispatch asynchronous HTTP GET requests. Response bodies are discarded using HttpResponse.BodyHandlers.discarding() to prevent unnecessary memory allocations.

9.2 RFC-4180 Compliant CSV Parser (Endpoint.java)

Replaces naive comma splitting with a stateful tokenizer that respects double-quote enclosures ("...") and escaped quotes (""), allowing endpoint names to safely include commas and special characters.

9.3 Mathematical Visible-Width Alignment (CLIFormatter.java)

Implements stripAnsi() using regular expressions (\u001B\[[;\d]*m) to calculate true display width, appending exact trailing spaces via padRight() so that ANSI colored labels never disrupt ASCII table borders.

12. Challenges Faced & Engineering Solutions

  1. Invisible ANSI Color Sequences Misaligning Tables: Standard printf counts invisible escape codes toward character width. Solved by developing stripAnsi() and padRight() to calculate true visible width.
  2. Atomic File Persistence Across Platforms: Direct file replacements on Windows can collide with filesystem lock handles. Solved by implementing atomic temporary file writing with fallback replacement handling.
  3. Unbounded Thread Spawning Under High Target Loads: Using an unbounded thread pool could trigger OS thread exhaustion. Solved by bounding the thread pool to available processor cores.
  4. Scanner Crashing on EOF: Standard Scanner.nextLine() throws NoSuchElementException on stream termination or non-interactive pipes. Solved by implementing a defensive readLineSafe() helper.

13. Learnings & Key Takeaways

  • Mastery of Modern Java Concurrency: Practical experience utilizing CompletableFuture, ExecutorService, and non-blocking HTTP clients for parallel network operations.
  • Clean Architecture & SOLID Principles: Implementing decoupled layers (Model, Repository, Service, Presentation) results in clean, extensible, and easily testable code.
  • Defensive Programming: Designing for failure by validating boundaries, handling timeouts, and implementing atomic persistence safeguards application resilience.
  • Terminal User Experience: Demonstrates that CLI applications can deliver a clear, intuitive visual experience without the overhead of heavy graphical frameworks.
